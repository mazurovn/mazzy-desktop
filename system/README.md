# system/ — Bluetooth/Wi-Fi для MediaTek MT7630E

Один чип, один MCU: Wi-Fi — PCIe `03:00.0` (`mt76x0e`), Bluetooth — USB `0489:e069` (ядро не знает ID →
`btusb new_id 0489 e069 0 0e8d 763f`).

- Системная часть (root, один раз): `pkexec sh system/install-bluetooth.sh`
- Пользовательская часть (юниты, конфиги, polkit): `./install.sh`
- Аудио и наушники: `mazzy-bt-audio status` (или `bash system/bt-audio.sh status`)
- Диагностика адаптера: `bash system/bluetooth-fix.sh status`
- Спеки: `openspec/specs/mt7630e-radio` (чип), `openspec/specs/bt-audio` (подключение, профили, выбор устройств)

## Два режима отказа адаптера

| Симптом | Диагноз | Лечение |
|---|---|---|
| `hci0: Opcode 0x0c03 failed: -110`, hci0 DOWN | HCI Reset timeout после загрузки | `mt7630e-bt-reset.sh usb` — power-cycle USB-порта (до 5 раз) |
| hci0 UP, наушники «подключены», звука нет, `hci0: link tx timeout`, `avdtp … Connection refused`, наушники сами отваливаются | ACL-канал мёртв (после тёплого ребута / пробуждения) | `mt7630e-bt-reset.sh chip` — **PCI bus reset** чипа (Wi-Fi пропадает на ~10 с) |

Для режима №2 **не помогают**: USB port power-cycle, `rmmod btusb`, PCI remove/rescan, `USBDEVFS_RESET`,
`hciconfig reset`, вендорная HCI `0xFCC3`. Проверено 2026-09-21 (btmon: 0 ACL RX, 0 Number of Completed Packets;
usbmon: bulk OUT URB не завершаются).

**Вердикт ACL.** Мёртв = есть активный линк, `TX acl` растёт, а `RX acl` так и остался **ровно нулём** — два тика
подряд (режим отказа после тёплого ребута: линк поднят, но с него не пришло ни одного пакета), либо
`hci0: link tx timeout` в журнале ядра за 10 минут. Нет подключённых устройств → `unknown`, сброс не выполняется
(раньше в этом случае печаталось `alive` — вердикт, которого детектор не проверял).

Правило «RX не вырос между тиками» **не годится** и было откатано 2026-09-23: при воспроизведении A2DP ноутбук
шлёт непрерывный поток, а обратно идут только редкие AVRCP/ACK — детектор объявил канал мёртвым и уронил чип
посреди музыки (Wi-Fi пропал на 10 с). Подробности — `openspec/changes/bt-audio-devices/measurements.md`.

## Подключение наушников: по событию, а не по таймеру

Раньше watchdog раз в минуту вслепую звонил всем спаренным наушникам: 12 с радио на попытку, `Host is down`
в журнале каждую минуту (53 строки в час), батарея наушников и ноутбука, и ручное «Отключить» отменялось
через минуту. Теперь:

- обратное подключение — дело самих наушников: `Trusted: yes` + `FastConnectable=true` + политика BlueZ
  (`AutoEnable`, `ReconnectAttempts`, `ReconnectIntervals`, `ReconnectUUIDs` в `60-mazzy-bluetooth.conf`);
- ноутбук подключает сам только по событию: старт сессии, пробуждение, сброс чипа, кнопка пользователя;
- ручное «Отключить» уважается: маркер `/run/user/<uid>/mazzy-bt/manual-off/<MAC>` живёт до перезагрузки
  или до явного «Подключить».

**Гонка BlueZ ↔ WirePlumber.** `bluetoothd` системный, а BlueZ-эндпойнты регистрирует WirePlumber в сессии
пользователя. Если наушники подключаются раньше, в журнале появляется
`a2dp-sink profile connect failed … Protocol not available`: устройство «подключено», но sink не появляется,
или остаётся только гарнитурный профиль (моно 16 кГц). Лечит пользовательский юнит `mazzy-bt-audio.service`
(`After=wireplumber.service`): дожидается PipeWire и переподключает **только те устройства, что уже подключены,
но без рабочих профилей** — это доли секунды, ACL уже есть; выключенные наушники он не трогает.
`mazzy-bt-audio.path` ловит тот же случай после сна и сброса чипа (root пишет `/run/mazzy-bt/trigger`).

## Аудио: `mazzy-bt-audio` (любые наушники, без хардкода MAC)

```
mazzy-bt-audio status                  # адаптер, ACL, устройства, профили, выход/микрофон
mazzy-bt-audio connect|disconnect      # с учётом «отключено вручную»
mazzy-bt-audio profile auto|a2dp|headset   # режим звука (без аргумента — показать текущий)
mazzy-bt-audio out|in                  # список выходов / микрофонов
mazzy-bt-audio out|in [номер|имя|ключ] # выбрать; ключ = node:… | port:узел:порт | bt:MAC
mazzy-bt-audio pair [MAC]              # найти и спарить наушники (сам отвечает на код подтверждения)
mazzy-bt-audio raw-scan 12             # что есть в эфире: MAC|имя|спарено
bash system/bt-audio.sh mic            # проверить микрофон (запись 3 с + уровень сигнала)
bash system/bt-audio.sh fix            # сброс чипа при мёртвом ACL + переподключение
```

Те же действия — в MAZZY Environment, страница «Звук и Bluetooth»: кнопка «Искать наушники», сопряжение,
подключение, режим звука, выбор выхода и микрофона, состояние адаптера с кнопками «Починить» и
«Полный сброс чипа». Страница берёт всё одним вызовом `mazzy-bt-audio raw-all` (300 мс на трёх устройствах).

**Наушники «включены», но их нет в списке.** Скорее всего снят бонд: `bluetoothctl info <MAC>` показывает
`Paired: no` при `Trusted: yes`. Наушники при этом честно пытаются подключиться, а BlueZ их отвергает. Лечится
повторным сопряжением — **зажать кнопку до мигания** (обычного включения мало) и нажать «Спарить». Спаренные,
но отключённые устройства видны в списках выхода и микрофона строкой «не подключено — подключить и выбрать»:
одно действие подключает и делает устройством по умолчанию.

**Сопряжение и код подтверждения.** Наушники подтверждают пару числовым кодом, и `bluetoothctl` спрашивает
«Confirm passkey … (yes/no)» асинхронно — ответ, скормленный заранее через пайп, теряется, и сопряжение падает
с `org.bluez.Error.AuthenticationFailed`. Поэтому `mazzy-bt-audio pair` управляет сессией через FIFO и отвечает
ровно в момент запроса. На одной паре три попытки обычным `bluetoothctl pair` провалились,
через FIFO — `Pairing successful` с первого раза. Устройства, известные BlueZ, но не спаренные, видны в списке
с кнопкой «Спарить» (например WH-CH520 после снятия бонда).

Режимы звука (выбор хранится в `~/.local/state/mazzy/bt-audio.conf`, секция на устройство —
в `~/.config/mazzy` нельзя: это симлинк в рабочее дерево репозитория, а MAC-адресам там не место):

- **Авто** — `bluetooth.autoswitch-to-headset-profile = true`: приложение открыло микрофон → гарнитура,
  закрыло → обратно стерео;
- **Стерео (A2DP)** и **Гарнитура (HFP/HSP)** — профиль фиксируется явно, автопереключение выключается.
  Настройка автопереключения в WirePlumber 0.5 **глобальная**, не по устройству: явный режим у одного
  устройства выключает автопереключение у всех.

**Выбор входа и выхода — это порты, а не только узлы.** У встроенной карты один источник с двумя портами
(`analog-input-internal-mic` и `analog-input-mic` — микрофон в разъёме), поэтому список строится из строк вида
`port:<узел>:<порт>`, а пустой разъём показывается как «недоступно · разъём пуст», а не прячется. Микрофоны
наушников попадают в список даже в профиле A2DP (строка `bt:<MAC>`): выбор переключает устройство в гарнитуру
с проверкой SCO и откатом. То же для выходов: динамики, наушники в разъёме, каждое BT-устройство.

**Ограничение Bluetooth (не баг):** одновременно A2DP-стерео и микрофон одного устройства невозможны — при
включении микрофона звук падает до моно телефонного качества. Стерео+микрофон есть только в LE Audio
(BT 5.2+, LC3); MT7630E — BT 4.0.

**Гарнитура проверяется, а не объявляется.** На MT7630E HFP нередко «подключается» на уровне RFCOMM, а SCO-канал
не поднимается: в журнале WirePlumber `Failure in Bluetooth audio transport`, счётчики `sco:` в `hciconfig`
стоят на нуле. В гарнитурном профиле через SCO идёт и воспроизведение, поэтому молчит всё. Команда
`mazzy-bt-audio profile headset` после переключения открывает микрофон на 2 с и смотрит счётчик SCO: нет
роста — возврат в стерео и сообщение «адаптер не отдаёт голосовой канал». Вердикт сохраняется в
`~/.local/state/mazzy/bt-audio.conf` (`[adapter] sco = broken`), и пока он отрицательный, режим «Авто» **не включает**
автопереключение WirePlumber: иначе приложение, открывшее микрофон (замечено с Firefox 2026-09-23), переводит
карту в HFP и глушит и музыку, и микрофон.

**Почему SCO не поднимается — разобрано до ядра (2026-09-23).** Трассировка WirePlumber
(`WIREPLUMBER_DEBUG='spa.bluez5*:T'`) показывает:

```
backend-native.c:2642 sco_do_connect: codec=MSBC        (и codec=CVSD — то же самое)
backend-native.c:2617 sco_create_socket: transparent=1  (и transparent=0 — то же самое)
backend-native.c:2759 sco_ready: acquire failed: Invalid request code (-56)
```

Тот же `-56` даёт **голый SCO-сокет** мимо PipeWire и BlueZ (тест `connect()` на `AF_BLUETOOTH/BTPROTO_SCO`
с `BT_VOICE` 0x0060 и 0x0003) — значит отказывает ядро, а не конфигурация. Совпадает с сообщением при
инициализации адаптера: `hci0: Failed to read local supported codecs (-56)`: ядро идёт путём
`Enhanced Setup Synchronous Connection`, которому нужен список кодеков контроллера, а MT7630E на эту команду
отвечает отказом, хотя в features рапортует `<transparent SCO>`, `<extended SCO>`, `EV4/EV5`.

Проверено на двух парах разных вендоров — одинаково; A2DP-стерео 48 кГц
при этом работает у обеих. Не помогли `bluetooth disable_esco=1` и `btusb force_scofix=1` (последний меняет
SCO MTU со `128:2` на `64:8`). Лечится только на уровне ядра (квирк вида
`HCI_QUIRK_BROKEN_ENHANCED_SETUP_SYNC_CONN` для этого устройства) либо внешним USB-донглом Bluetooth.

**Донгл решает вопрос.** С Realtek RTL8761BU (`0bda:a729`, BT 5.3) гарнитурный профиль поднимается штатно:

```
backend-native.c:2642 sco_do_connect: codec=MSBC
backend-native.c:2765 sco_ready: acquire complete, read_mtu=64, write_mtu=64
hciconfig hci2: sco:4641 -> 6247 (приём растёт)
```

То есть микрофон Bluetooth-гарнитуры работает — просто не на встроенном MT7630E.

На донгле гарнитура заработала на обеих парах. Промежуточные отказы одной из них (`-110/-111`) оказались
следствием подвисшего донгла (`hci2: HCI reset during shutdown failed`) и оставленного с прошлых
экспериментов `bluetooth.disable_esco=1` — после сброса параметров в значения по умолчанию всё поднялось.
Вывод: параметры ядра из диагностики обязательно возвращать обратно, иначе они сами становятся причиной.

Вердикт SCO всё равно хранится по паре «адаптер + устройство» (`[dev:<MAC>@<адаптер>] sco`): отказывать
может и адаптер, и конкретные наушники. Вывод «адаптер не умеет SCO» делается только после провала
минимум двух разных пар.

**Грабли:** ключи `bluez5.codecs`, `bluez5.enable-msbc`, `bluez5.enable-hw-volume` в `51-bluez-headset.conf`
валят монитор BlueZ целиком — наушники пропадают из PipeWire вообще. Не добавлять (проверено 2026-09-22).

**Конфиг WirePlumber — один:** `config/wireplumber/wireplumber.conf.d/51-bluez-headset.conf`, ставится симлинком
из `install.sh`. Старый `51-bluez-a2dp-only.conf` удалён (2026-09-23). Скрипты в `~/.config/wireplumber` не пишут:
это симлинк в репозиторий, и запись означала бы правку рабочего дерева git.

## Несколько адаптеров

Встроенный чип и USB-донгл живут одновременно; номер `hciN` у донгла меняется при переподключении
(видели `hci1`, потом `hci2`), поэтому выбранный адаптер хранится по BD-адресу в
`~/.local/state/mazzy/bt-audio.conf` (`[adapter] use`). Команда — `mazzy-bt-audio adapter [hciN|MAC|имя|auto]`,
в MAZZY Environment — группа «Адаптер Bluetooth».

**По умолчанию выбор автоматический (`[adapter] mode = auto`): вставленный донгл становится основным.**
Правило простое и без привязки к вендору: адаптеры с заведомо сломанным SCO (`[adapter:<MAC>] sco = broken`)
уходят в конец, из остальных побеждает появившийся позже — горячо подключённый донгл всегда получает номер
`hciN` больше встроенного. Явный выбор в меню закрепляет адаптер (`mode = pinned`), «Выбирать автоматически»
возвращает автоматику. Если закреплённый адаптер вынули, система не остаётся без Bluetooth — берётся лучший
из оставшихся. Горячее подключение ловит udev-правило `91-mazzy-bt-adapter.rules`: оно дёргает
`/run/mazzy-bt/trigger`, и пользовательский юнит переприменяет выбор и возвращает наушники.

Грабли, на которые наступили:

- **Пары BlueZ у каждого адаптера свои.** Переключение на донгл до сопряжения оставляет систему без
  наушников. Поэтому списки устройств собираются **со всех адаптеров** (в строке видно, где спарено),
  «Подключить» сам переключает адаптер на нужный, а при выборе адаптера без спаренных наушников
  выводится предупреждение.
- **Одно устройство может быть спарено на обоих адаптерах.** Тогда действие идёт на текущий адаптер,
  иначе «Подключить» уводит систему обратно на встроенный чип.
- **`[Policy] AutoEnable=true` включает все адаптеры обратно** после перезапуска `bluetoothd`, поэтому
  выбор переприменяется при старте сессии (`mazzy-bt-audio session`).
- **Watchdog не должен «чинить» намеренно выключенный адаптер.** При выборе донгла встроенный чип гасится
  (`Powered=false`), а `mt7630e-bt-reset.sh auto` видел `hci0 DOWN` и каждую минуту поднимал его обратно
  power-cycle'ом порта (3–14 с на тик). Теперь режим `auto` сначала проверяет `Powered` через D-Bus и при
  выключенном пользователем адаптере ничего не делает.
- **Установщик перезапускает `bluetoothd` только при изменении его конфига** — иначе каждая переустановка
  скриптов рвала все активные соединения.
- **Одно устройство может быть спарено на нескольких адаптерах** — в списках оно показывается один раз,
  приоритет у текущего адаптера (иначе статус брался из строки другого адаптера и врал).
- **`busctl --json` не годится для чтения дерева BlueZ:** дамп падает целиком
  («Failed to dump DBus message to JSON object»), стоит появиться в эфире BLE-устройству с бинарной
  рекламой. Читаем обычный plain-вывод `busctl get-property`.

## Привилегии

`pkexec` + правило `50-mazzy-connectivity.rules` (`/usr/share/polkit-1/rules.d/`): локальному пользователю из
группы `sudo` разрешены без пароля только `mt7630e-bt-reset.sh`, `mt7630e-bt-watchdog.sh`, `mazzy-vpn`.
Чтение пароля из файла (`sudo -S < ~/Documents/sudo.txt`) удалено из всех скриптов 2026-09-23 — репозиторий
публичный. Файл `~/Documents/sudo.txt` можно удалить вручную, скрипты его больше не читают.

## Файлы

- `mt7630e-bt-reset.sh` — `chip` (по умолчанию) / `usb` / `auto` (chip только при мёртвом ACL, ≤ 1 раз в 10 мин,
  флаг `/run/mt7630e-chip-reset.stamp`) / `acl-check` / `save-connected` / `trigger`.
- `mt7630e-bluetooth.service` — при загрузке `chip`, до `NetworkManager` (сеть ещё не поднята → VPN не рвётся).
- `mt7630e-bt-watchdog.{sh,service,timer}` — раз в минуту только медицина чипа: `auto` + жив ли `bluetoothd`.
  Наушники не подключает (см. выше).
- `mt7630e-bt-sleep.sh` — `pre`: снимок подключённых устройств; `post`: `chip` + триггер переподключения.
- `mazzy-bt-audio.sh` → `/usr/local/bin/mazzy-bt-audio` — подключение по событию, профили, выбор выхода/микрофона,
  машинный вывод `raw-*` для MAZZY Environment.
- `mazzy-bt-audio.{service,path}` + `mazzy-bt-audio-trigger.service` — пользовательские юниты (`systemd --user`).
- `bt-audio.sh` — интерактивная обёртка: сопряжение, проверка микрофона, починка.
- `bluetooth-fix.sh` — диагностика: адаптер, ACL, сервисы, совпадение установленных скриптов с репозиторием.
- `90-mt7630e-bluetooth.rules` — new_id при появлении устройства; `bluetooth-override.conf`,
  `60-mazzy-bluetooth.conf`, `50-mazzy-connectivity.rules`.

## Wi-Fi

Вне `chip`-сброса драйвер `mt76x0e` никто не трогает. Чип только 2.4 ГГц (1×1 b/g/n); помехи Wi-Fi↔BT — не причина
мёртвого ACL (проверено с выключенным Wi-Fi). `RF read failed: -110` и WARN в `mt76x02_mac_process_rx` — известные
шумы драйвера, на связь не влияют.

## Broadcom BCM20702 (USB 13d3:3404): наушники подключаются и отключаются

Причина: `btusb` прописан в `/etc/modules-load.d/btusb.conf` и грузится из initramfs, а dracut
не кладёт туда патч прошивки `brcm/BCM20702A1-13d3-3404.hcd` — чип остаётся на ROM-прошивке
(`build 0000`), соединение рвётся (`Host is down`).

- `dracut-bcm-bt-firmware.conf` → `/etc/dracut.conf.d/bcm-bt-firmware.conf`, затем `sudo update-initramfs -u`.
  Проверка: `sudo lsinitramfs /boot/initrd.img-$(uname -r) | grep BCM20702`.
- Страховка: `bcm-bt-firmware-guard.sh` → `/usr/local/sbin/`, `bcm-bt-firmware-guard.service` →
  `/etc/systemd/system/` (enable). Если патч при загрузке не применился — перезагружает `btusb`.
- Проверка после загрузки: `journalctl -k -b | grep "hci0: BCM20702A1"` — должно быть `build 1479`.
